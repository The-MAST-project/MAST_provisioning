# The PowerShell driver is retired, and Python is the only control plane

**Why:** `2026-07-12-port-server-orchestration-to-python.md` kept `server/check-and-provision.ps1` in the tree deliberately, and named the condition on which it would retire: it "remains authoritative until the Python driver is validated on a real run; then it retires." That condition has been met. The Python driver has been provisioning the production units since the 2026-08-09 migration runs, and drove the first full-set provisioning of the fleet on 2026-08-11 — the run behind `2026-08-11-verifies-assert-what-provisioning-owns.md`.

The strongest evidence is not that those runs succeeded but *what they found*. Every provisioning defect closed in that window was surfaced by a Python-driven run against real units, and each is anchored in Python: `#63` (`fully_provisioned` read true off a `--modules` subset build) diagnoses `driver.py`'s `_resolve_modules` handing a filtered set to the build, measured on mast03; `#70` (units reaching the prov server through a stale APIPA `hosts` entry, so no unit could transfer) came off a real `TRANSFER_FAIL unit=mast03 reason=net_use_failed rc=2`; `#60`, `#68` and `#69` came off the full-set fleet run. A driver that has found and survived that much on production hardware is validated in the sense the port record meant.

Meanwhile two drivers is not a neutral hedge. The tree carried 1156 lines of PowerShell driver plus five `server/lib` helpers only it dot-sourced, each with a Python port already in use and each with its own Pester suite — so a fix to lease reclaim, proxy assertion, log retention, staging-size accounting or link-flap classification had to be made twice or knowingly left asymmetric. It was already asymmetric: item 6's detached execute and item 8's loop mode were built natively in Python and never existed in PowerShell, so the nominally-authoritative driver had been the less capable one for weeks, and every fleet run of the last fortnight went through the other one. The fallback nobody exercises is not a fallback; it is a second definition of correct behavior that quietly drifts from the first.

This record therefore **executes** the earlier one rather than revising it, which is why `2026-07-12-port-server-orchestration-to-python.md` is not marked `superseded`: its account of the port, the scope boundary, and the SSH-first transport all still hold, and its own text anticipated this step.

**What:** `server/check-and-provision.ps1` and `server/install-scheduled-task.ps1` are deleted, as are the five helpers only the driver dot-sourced and the five Pester suites covering them: `mast-log-archive.ps1` (→ `prov/retention.py`), `mast-timezone.ps1` (→ `prov/maintenance_window.py`), `mast-winrm-warn.ps1` (→ `prov/winrm_flap.py`), `mast-staging-size.ps1` (→ `prov/staging_size.py`) and `mast-proxy-assert.ps1` (→ `prov/proxy_assert.py`). Each port is imported by `prov/driver.py` and covered by a pytest suite, with one exception noted below.

`server/lib` keeps what other callers use, and the split is now legible: `mast-log.ps1` is dot-sourced by the providers, `mast-net.ps1` and `mast-modules.psm1` by `build-mast.ps1`, `provisioning.psm1` by the providers, and `preflight-smb.ps1` by both `setup-smb-share.ps1` and `Driver._preflight_smb`, which invokes it as a Windows-only step. Pester's remaining scope is the build and the unit-side scripts — the code that still runs on Windows — and pytest's is the server. That was the intent of the three-job CI; it is now also true of the file layout.

One live call site broke and was fixed rather than found later: `client/onboard-mast-unit.ps1` Stage 1 ran the PowerShell driver by path on the prov server over a `PSSession`. It now resolves `python.exe` (then `py.exe`) with `Get-Command` and invokes `server/check_and_provision.py --only-hosts <host> --force [--modules ...]`, throwing a message that names the missing prerequisite when no interpreter is found. Resolving the interpreter explicitly rather than trusting `PATH` matters here because the session is a remote one under a different logon.

`install-scheduled-task.ps1` goes because the cadence moved *inside* the driver: `--loop` is a supervised long-lived process, not a task fired every 30 minutes, and the wrappers for both platforms already ship in `server/deploy/`. `server/deploy/README.md` had predicted exactly this ("once the PowerShell driver is retired") since 2026-07-12.

The docs were rewritten to describe the shipped state rather than the intended one. In `autonomous-provisioning-requirements.md` that meant more than a rename: the *Running the provisioning server on Linux* section was a speculative assessment of a port that has since happened, so it now records what shipped (the driver, the transport, `zoneinfo` timezones, `MAST_SERVER_ROOT` paths, the service wrappers) and what remains Windows-coupled (Samba for the staging share, and `build-mast.ps1`'s `robocopy` / `mklink` / `Get-PSDrive` / `WindowsPrincipal` calls, which a Linux prov server would need `pwsh` plus tool swaps to run). The scheduling and long-lived-service components moved from target to `[DONE]`, with the two pieces that genuinely did *not* ship called out: there is no `sd_notify` watchdog and no self-recycle bound. `docs/provisioning-server-setup.md` Step 7 installs an NSSM service instead of registering a scheduled task, and its runbooks use the Python CLI's flags.

**Rejected:**

- **Keep the PowerShell driver until a fleet run proves the Python one.** The position held while both were maintained, and it is what the 2026-07-12 record chose. It stopped paying once the Python driver gained capabilities the PowerShell one lacks — a rollback would now cost the detached execute and the loop, so the branch it protects is one nobody would take. Against that, the ongoing cost is two homes for every control-plane fix and a permanent question of which is authoritative.
- **Keep the five `server/lib` helpers, delete only the driver.** They are small and pure, and Pester coverage is cheap. But nothing would call them: a helper whose only caller is gone is untested against real use no matter how green its suite, and the next person to touch lease or proxy logic would have to decide, unprompted, whether to update the PowerShell copy. Deleting the caller and keeping the callee is how a codebase acquires plausible-looking dead code.
- **Port `install-scheduled-task.ps1` to register a task that runs the Python CLI.** A working Windows path with less setup than NSSM. Rejected because it re-splits supervision across two mechanisms — the loop's own cadence and the task's trigger — and the loop already owns cadence, graceful stop, and sequential cycles. A task firing `--loop` would be a supervisor that cannot supervise; a task firing one cycle would give up everything item 8 built.
- **Delete `vm/run-prov-test.py` in the same pass**, since its own docstring says it retires when the autonomous driver works. Out of scope: it is the dev-cycle harness and is still what the VM scenarios drive. Its docstring was corrected to point at `server/prov/driver.py`, and the decision to retire it is left to whoever replaces the harness.

**Unsettled:**

- **What the fleet runs prove is the one-shot cycle, not the unattended cadence.** The production evidence is of `Driver.run()` invoked per run against real units. `--loop` as a supervised service has only run on the VM (two dry-run cycles), and no service wrapper is installed on a prov server yet, so the cadence, the graceful-stop path under a real supervisor, and the behavior of a cycle that throws mid-fleet are still unexercised in production.
- **Individual paths remain unexercised even so.** Session-drop reconnect, reboot survival under `-AllowReboot` (in-place VM reboots do not return reachable — a VirtualBox harness artifact), and the proxy re-introduction the end-of-run assert exists to catch have not fired on real hardware. The PowerShell fallback that nominally covered them is now gone, but it never exercised them either.
- **`prov/winrm_flap.py` is imported by nothing.** Its PowerShell counterpart was live in the retired driver, where the WinRM link-flap warnings arrived on a stream the Python transfer path does not produce (transfer is synchronous). Deleting the PowerShell one leaves a tested but unused port; it stays because the deferred live `TRANSFER_PROGRESS` / `WINRM_LINK_FLAP` capture is the thing that will use it, tracked on #10 item 9.
- **The dev harness still speaks WinRM.** `vm/vm_lib.py` re-exports `prov.transport`, but `run-prov-test.py` and the scenarios were written around the WinRM path, so retiring WinRM (also tracked on item 9, with #6's transport decision) will touch the harness rather than only the driver.
- **The onboarder's Python resolution is untested on a real prov server.** `Get-Command python.exe` under a remote `Negotiate` session returns whatever that logon's `PATH` holds, which is not the interactive operator's: a per-user install or a venv would not be found, and on a stock Windows image the first `python.exe` on `PATH` can be the WindowsApps App Execution Alias, which is not an interpreter at all. If it misses in the field, the fix is likely an explicit interpreter path in the prov-server convention alongside the repo location.

**Implications:**

- There is one control plane, and new server-side orchestration belongs in Python. `CLAUDE.md` says so directly now instead of describing a port in progress.
- The Pester job's scope shrank from eleven suites to six. That is the intended shape, not a loss of coverage — the five that went had already been superseded by pytest equivalents — but it does mean the Windows-only signal is now narrower, and a regression in server-side logic can only be caught by pytest.
- `#10` item 9's "still to land" list is one item shorter, and what remains on it (live progress/flap capture, unit-side no-BOM writers, WinRM removal) no longer has a PowerShell driver to be blocked behind.
