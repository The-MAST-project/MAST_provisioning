# Per-user desktop state is written into the target hive and re-asserted at every logon

**Why:** `#54` asks for two things on a machine that lives in a dome and is reached over NoMachine: a dark Windows theme, night-vision-friendly at the telescope, and a dark background carrying the machine's identity -- above all the hostname -- so a remote session can tell at a glance which unit it is looking at. Both are `HKCU` settings belonging to the autologin `mast` account, and provisioning runs over WinRM as an administrator or as SYSTEM. Nothing in the provider model addressed that gap; the ticket guessed at "the first-logon apply task or a default-user-hive write at bootstrap," and neither is quite what the machines need.

**What:** one provider, `server/providers/desktop-appearance/`, at order 2750 -- after `desktop-shortcuts` (2700) so the operator-desktop modules sit together, and far after `config-bootstrap` (150), whose `C:\WIS\config.toml` supplies the site and role on the image. It carries three separable pieces, and the separation is the design:

`render-desktop-background.ps1` draws the background with `System.Drawing` into `C:\ProgramData\MAST\desktop\background.png` -- machine-wide, once. It draws only what it is handed and decides nothing about where it came from; `Get-MastAppearanceFields` in `mast-appearance-lib.ps1` derives the set: the hostname, the site spelled out ("Neot Smadar" rather than the `ns` the config carries), and the site coordinates formatted to four decimals from the `[location]` block. Site comes from the deployed config, never from the hostname, per the standing rule. A field that resolves to empty drops its line rather than printing a placeholder, so the block closes up around it. The sidecar `background.json` records what was drawn plus a `${RendererVersion}`, which is what makes staleness detectable at all.

`machine_role` is deliberately **not** on the image. It was, in the first draft, and it said `role unit` directly above a footer already reading `MAST unit`.

One derivation in that lib is worth naming because it had a wrong-looking easy answer: the site display name is a map in the lib rather than a `site_name` key added to `config-bootstrap`'s `sites\*.toml`. That file is cross-checked against the controller's MongoDB `sites` document at app startup, and a new key there is a risk taken on behalf of a wallpaper label.

The coordinates are formatted through `InvariantCulture` rather than with a bare `'{0:F4}'`, which honours the current culture -- a comma decimal separator would render the position as nonsense. Bootstrap pins en-US, so this is belt and braces; it costs one explicit argument and does not depend on that pin having held.

The geometry is crop-safe rather than centered-looking. `WallpaperStyle` is 10 (Fill), which scales to cover and discards the surplus, so a 1440x1080 desktop -- a NoMachine window dragged squarish with remote-resize on -- loses 240 px from each side. At the first draft's `${Margin} = 140` that band contained the accent bar and the first glyphs of the hostname: the one thing the background exists to show was the first thing cropped. The margin is 300, which leaves 60 px of slack inside the 4:3 safe area. A 16:10 desktop crops only 93 px per side and survived either way, which is why this was an assumption in the first version of this record rather than a caught bug -- drawing a proof of the layout is what made the arithmetic obvious.

`mast-userhive-lib.ps1` resolves the target user's hive: mounted at `HKEY_USERS\<sid>` when the account is signed in, or `reg.exe load`ed from its `NTUSER.DAT` when it is not. On a provisioned unit the mounted case is the *normal* one, not an error path -- bootstrap enables Winlogon auto-logon for `mast` (2026-06-29), so from the first boot onward that hive is in use and `reg.exe load` cannot touch it. `Resolve-MastUserHive` returns `$null` only when the account has no profile at all, and throws with `reg.exe`'s exit code when a profile exists but its hive cannot be reached. It has no `HKCU:` fallback by construction.

`apply-desktop-appearance.ps1` runs as `mast` from an AtLogon scheduled task, `MAST-DesktopAppearance-Apply`. It exists for the two things a registry write cannot do: `SystemParametersInfo(SPI_SETDESKWALLPAPER, ...)` to repaint the desktop and a `WM_SETTINGCHANGE` / `ImmersiveColorSet` broadcast to make the shell re-read the theme. Both must originate inside the session. `provide-desktop-appearance.ps1` starts the task immediately when it found the hive already mounted, so the change lands without waiting for a sign-in.

Two departures from the nearest precedent are deliberate. `apply-instrument-profiles.ps1` is one-shot -- sentinel plus self-unregister -- because it materializes files once. This task is neither: appearance is standing state, re-rendered when the machine is renamed or the design changes, and every reboot needs the broadcast again, so a sentinel would pin whatever the first logon happened to see. And the values are written **twice**, once into the hive from provisioning and again by the task in-session; that is not redundancy but the two halves of the problem -- provisioning can reach the registry and not the desktop, the task can reach both but only exists once someone signs in.

`verify-desktop-appearance.ps1` answers *is it current?* rather than *is it present?*, which resolution rule 2 in `docs/per-module-tracking-plan.md` requires of exactly this kind of generated artifact. It compares the sidecar's static fields against the live machine -- so a renamed unit reports `background STALE` instead of quietly keeping an image that names the wrong host -- and compares all five deployed registry values against what this build writes, reading them back through the same resolver the provider wrote through, so the check cannot be inspecting a different user than the one configured.

**One defect the dev VM caught, worth recording because the diagnosis was invisible.** `apply-desktop-appearance.ps1` compiles its two `user32.dll` entry points with `Add-Type -MemberDefinition`, and the first version passed `-UsingNamespace 'System.Runtime.InteropServices'`. `Add-Type` emits that same `using` directive itself, the C# compiler warns about the duplicate, and `Add-Type` treats the warning as an error -- so the task threw at its first statement. The compile also sat *outside* the script's `try`, so nothing was logged: the module reported success, `apply.log` did not exist, and the only trace on the whole machine was the scheduled task's `LastTaskResult = 1`. Two changes came out of it beyond the one-line fix: the compile moved inside the `try` so a failure reaches the `catch`, and both `provide` (which waits for the task it starts) and `verify` now judge `LastTaskResult` instead of mere registration. A registered task that fails every logon leaves the desktop untouched while every other check passes, which is the shape of failure this provider is most exposed to.

**Rejected:**

- **Sysinternals BGInfo**, which is the obvious answer and was the first recommendation. It ships already: `Bginfo64.exe` is inside `server/providers/sysinternals/assets/SysinternalsSuite.zip` and lands on `PATH`. Its configuration is a **binary `.bgi`**, authorable only through its GUI -- an asset nobody can read, diff or amend in review, in a repo whose per-module hashes and decision records exist to make changes legible. Its one real advantage is live fields, and `#54` asks for *static* information. The seam is left open rather than closed: dynamic content lands in the renderer and in the sidecar's `dynamic_fields` list, which verify skips, and moves the image from one machine-wide copy to a per-user one -- a change to `apply-desktop-appearance.ps1` alone, since that script already reads the image path out of the sidecar rather than from a constant.
- **A default-user-hive write at bootstrap**, the ticket's other suggestion. It seeds only profiles created afterwards, and `C:\Users\mast` already exists on every provisioned unit -- so on today's fleet it would reach nothing. Not built as a supplement either, since no future account on a unit needs it yet.
- **A one-shot AtLogon task doing all the work**, matching `instrument-profiles` exactly. Simpler to copy, and it would leave the theme un-applied on any unit until someone signed in, with nothing machine-side to verify against in the meantime.
- **Rendering into the user profile** (`%LOCALAPPDATA%`) instead of `C:\ProgramData`. It is where BGInfo would put it and where the dynamic path will eventually go, but a per-user image cannot be verified from a provisioning session that has no such session, and the non-elevated task cannot write to a ProgramData folder SYSTEM created -- so today the machine copy is the artifact and the task only points at it.
- **Restarting `explorer.exe`** to make the last few shell surfaces follow the theme immediately. Provisioning may be running against a session someone is watching.
- **`WallpaperStyle` 6 (Fit)** instead of a wider margin, which letterboxes rather than cropping and would make the margin question moot. Bars around the image look careless on a machine whose whole point is looking deliberate.
- **A payload version stamp on the image -- built, then removed.** The image carried the provisioning commit the payload was built from, read as a short `git_sha` from the *staged* `build-manifest.json` (not `installed-manifest.json`, which at order 2750 still describes the previous run, and not `built_at`, which the driver rotates on every rebuild and which would therefore have drifted the module forever). It was pulled before this landed, on the judgment that there is nothing durable to name yet: `MAST_provisioning` carries **zero git tags**, so `git describe` returns a bare SHA, and a seven-character hash is not a version an operator can act on. The mechanism is small and the reasoning above is the whole of it, so re-adding it once real versioning exists is cheap. Until then the desktop states *when* a unit was provisioned and not *what with*, which is the honest gap recorded under `Unsettled`.

**Unsettled:**

- **Verified on the dev VM (`MAST-WIS-01`, 2026-08-19), not on a unit.** A `--modules desktop-appearance` cycle rendered the image (1920x1080, `Format32bppArgb`), wrote all five values into the signed-in `mast` hive at `HKEY_USERS\<sid>`, registered and ran the task cleanly, and passed verify. The staleness checks were exercised rather than assumed: a sidecar rewritten to a different hostname produced `background STALE: computer_name rendered as 'MAST-RENAMED-99', machine reports 'MAST-WIS-01'` and exit 1, a hand-changed `WallpaperStyle` produced `WallpaperStyle is '0', build expects '10'`, and restoring both returned it to `PASS`. What a unit adds over the VM is real hardware, the `ns` site profile, and the LTSC image.
- **The theme reaches applications immediately but the shell only at the next logon.** Measured, not believed: after the provisioning run the wallpaper was live and correct while the taskbar was still light, and after a reboot with auto-logon the taskbar, search field and tray were all dark. This is benign in practice because the values are in the hive *before* Explorer starts on every subsequent boot -- the incomplete state exists only in the session provisioning itself interrupted, and the run requests a reboot anyway. It is also why `explorer.exe` is not restarted.
- **The 4:3 crop reasoning held on real geometry, by luck of the test bed.** The VM's desktop is 1024x768, so the screenshot *is* the Fill-crop case: the accent bar and hostname sit inside the retained area with the margin at 300, where at the original 140 the bar would have been cropped off entirely. What is still untested is a NoMachine session resized to something squarer still.
- The claim that `reg.exe load` fails on a signed-in user's hive remains reasoned from the locking rather than observed -- every VM run found the hive already mounted, which is the path a provisioned unit always takes. The `reg.exe load` branch is therefore the *unexercised* one. `#106` carries the same uncertainty for `bootstrap-winrm.ps1`.
- `Segoe UI` rendered correctly on the VM's Windows 11 image. Its presence on the units' Windows 10 IoT Enterprise LTSC image is still unconfirmed, and `System.Drawing` substitutes silently rather than failing.
- A concern that turned out not to exist, recorded so it is not re-litigated: `C:\ProgramData\MAST\desktop` was expected to be unwritable by the non-elevated task, since SYSTEM creates it. Measured ACL is `BUILTIN\Users Allow Write`, and a write as `mast` succeeded -- so `apply.log` and any future per-user render need no ACL work.
- **The background says nothing about what a unit is running**, only when it was last provisioned. An operator reading the desktop cannot tell a machine on a three-week-old payload from a current one; that answer lives in `installed-manifest.json` and the fleet drift report. This is deliberate for now (see `Rejected`) and is the first thing to revisit when the repo has versioning worth printing.
- Nothing renders the site elevation, which `[location]` also carries. Two coordinates were what was asked for; a third line was not.

**Implications:** `Get-MastAppearanceFields` is called by the provider to render and by the verify to compare, which is the only reason the staleness check means anything -- two independent readings of "what should be on the image" would prove that two copies of the formatting agree with each other, not that the image matches the machine. `mast-userhive-lib.ps1` is the first shared answer in this repo to "write a per-user setting from a provisioning run," and the `-lib.ps1` suffix puts it under `test_provider_commandfiles.py`'s staging guard automatically. `client/bootstrap-winrm.ps1`'s `Set-MastHkcu` has the defect this lib is built not to repeat -- it silently retargets the administrator's hive when the load fails -- and is `#106`, fixed locally rather than by sharing this code, because bootstrap runs before any staging exists. The remaining `#54` item is the observatory-ready sweep (lock screen, night light, screen-off policy), which this provider is the natural home for.
